Phase 1
Scope Identification
Define scope
  • Target files and audience
  • Scope and success criteria
  1. Identify the target codebase / modules (e.g. SamplePythonAPI/app/)
  2. Determine audience (developers, API consumers, new hires) and doc depth
  3. Set success criteria and project boundaries
⚙ Agent Action
Receives the project path, scans file types (.py, .rst, config files), and proposes a scope boundary document for human approval before proceeding.
Phase 2
File / Logic Analysis
Understand code
  • Map modules and APIs
  • Trace dependencies
  1. Parse the AST for each Python module (main.py, api.py, models.py, database.py, ui.py)
  2. Map class and function dependencies (e.g. TicketRepository ↔ Ticket)
  3. Identify public APIs, entry points, and data models
⚙ Agent Action
Walks the codebase, builds a symbol dependency map, classifies each module by role (API layer, data layer, UI layer, models), and produces a structured summary that feeds into Phase 3.
Feedback from Phase 3: missing context triggers re-analysis
Phase 3
Inline Documentation
Write docstrings
  • Update docstrings
  • Add missing annotations
  1. Generate / update Google-style module and function docstrings
  2. Verify and add type annotations where missing
  3. Insert contextual inline comments for complex logic
⚙ Agent Action
Writes docstrings for every public symbol, inserts module-level docstrings, validates them with a parser, and returns a diff for human review.
→ Feedback to Phase 2: re-analyze if undocumented symbols found
← Feedback from Phase 4: Sphinx warnings trigger doc fixes
Phase 4
Sphinx Generation
Build docs
  • Run autodoc and build
  • Capture warnings
  1. Configure Sphinx — create conf.py, index.rst, extension list
  2. Run sphinx-apidoc to auto-generate RST source files
  3. Build HTML output via sphinx-build
  4. Collect build warnings and broken cross-references
⚙ Agent Action
Scaffolds the Sphinx project structure, invokes sphinx-apidoc and sphinx-build programmatically, captures stdout/stderr, and classifies warnings for triage.
→ Feedback to Phase 3: fix inline docs on warnings
Phase 5
Review & Maintenance
Verify and iterate
  • Human review
  • Re-run on updates
  1. Human reviewer checks generated docs for accuracy, completeness, and tone
  2. Fix any remaining warnings or broken references from the Sphinx build
  3. Set up CI hooks (pre-commit, GitHub Actions) to re-run the pipeline on code changes
⚙ Agent Action
Surfaces a structured review document (diff of new/changed docstrings, list of Sphinx warnings resolved/unresolved), and registers a CI task that re-triggers the full pipeline on every push to main.
→ Feedback to Phase 1: code changes restart the workflow

Feedback Loops

Phase 3 → Phase 2
Missing context or undocumented public symbols discovered during docstring generation triggers re-analysis of the relevant modules.
Phase 4 → Phase 3
Sphinx build warnings — missing docstrings, broken references, RST errors — loop back to fix inline documentation before re-running the build.
Phase 5 → Phase 1
When code changes are merged, the CI hook sends the agent back to Phase 1 to re-scope and re-run the entire documentation pipeline.
